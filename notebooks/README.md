# Notebooks vs. Scripts

The required experimental workflow (EDA, candidate generation, model
experimentation, Bayesian optimisation, HMM/Viterbi evaluation) is
implemented as plain, importable Python scripts/modules instead of
notebooks, so the exact same code path is used for development, the
technical report's figures, and the live API — there is no risk of a
notebook producing numbers that drift from what the deployed system does.

| Workflow stage | Script / module |
| --- | --- |
| EDA, dataset inventory, sample Folium map | `scripts/run_eda.py` |
| Candidate generation + feature engineering | `src/data/build_dataset.py` |
| Model experimentation & comparison (6 models) | `src/models/train.py` |
| Bayesian hyperparameter optimisation | `src/models/bayesian_opt.py` |
| HMM / Viterbi route reconstruction | `src/reconstruction/{graph,viterbi}.py`, exercised via `src/pipeline.py` and evaluated in `src/models/sequence_eval.py` |
| End-to-end orchestration | `scripts/run_full_pipeline.py` |

If you prefer to explore interactively, open a Jupyter kernel and import
from `src` directly, e.g.:

```python
from src.data.build_dataset import build_partition
from src.config import TRAIN_DIR
df = build_partition(TRAIN_DIR, "train")
df.head()
```

All figures referenced in the technical report are regenerated by running
the scripts above against `artifacts/results/` and `reports/figures/` -
nothing in the report is hand-drawn or fabricated.
